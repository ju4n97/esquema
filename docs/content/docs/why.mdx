# Why hclapi

hclapi is designed for creating HTTP APIs over databases and upstream services without writing boilerplate routing, connection pooling, validation models, or DTO mapping layers.

An API is defined in standard HashiCorp HCL manifests, keeping queries, input validation, and transformations close to the routes that use them.

## What it provides

:::info Co-located logic
Route definitions, SQL queries, input validation rules, and response shapes live together in clear HCL blocks rather than being scattered across routers, controllers, and ORM files.
:::

:::info Zero-drift documentation
OpenAPI 3.1 specifications are generated from the compiled manifest at boot time. Documentation and interactive UI portals (Scalar, Swagger, Redoc, Elements) are always in sync with your runtime constraints.
:::

:::info Parameter safety
SQL inputs are rewritten into prepared statement bind variables (`$1`, `?`, `@p1`) using single-pass lexical scanning. Query parameters cannot be injected, and string literals like `'admin@example.com'` remain untouched.
:::

:::info Sandboxed transformations
Starlark scripts run in an isolated virtual machine without host filesystem or network access, capped at a strict 100,000 instruction budget to prevent runaway loops.
:::

:::info Observability out of the box
Every route and step automatically emits OpenTelemetry spans and metrics, while structured `slog` output scrubs configured sensitive fields (like tokens or passwords) at emission time.
:::

## Where it doesn't fit

hclapi is not an all-purpose web framework. Use traditional application code when your service requires:

- Background worker loops or message bus consumers (Kafka, RabbitMQ).
- Long-lived stateful connections (WebSockets, gRPC bidirectional streams).
- Complex multi-step database schema migrations (use dedicated tools like `flyway` or `golang-migrate`).

A `step "go"` block is available when an endpoint requires third-party SDK calls or very customized logic.
