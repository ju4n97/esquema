# starlark

The `starlark` step runs data transformation logic inside an isolated, deterministic Starlark virtual machine. Scripts are precompiled once at boot time with zero runtime parsing overhead.

```hcl
starlark "sanitize" {
  source = <<-STARLARK
    def execute(ctx):
      body = ctx["request"]["body"]
      clean_email = body.get("email", "").strip().lower()
      return {
        "email": clean_email,
        "domain": clean_email.split("@")[-1],
      }
  STARLARK
}
```

## Attributes

| Attribute | Type     | Required | Description                                         |
| :-------- | :------- | :------: | :-------------------------------------------------- |
| `source`  | `string` |   yes    | Inline Starlark script defining `def execute(ctx):` |
| `when`    | `bool`   |    no    | Conditional expression                              |

## Exported outputs

| Field                 | Type  | Description                      |
| :-------------------- | :---- | :------------------------------- |
| `steps.<name>.result` | `any` | Value returned by `execute(ctx)` |

## Sandboxing rules

1. **No host access**: Starlark cannot touch the host filesystem, environment variables, or network sockets.
2. **Instruction limit**: Execution is capped at 100,000 steps. Runaway loops or unbounded recursion halt immediately with an error rather than hanging your server.
3. **Context access**: The `ctx` argument provides dictionary access to `ctx["request"]`, `ctx["timestamp"]`, `ctx["now"]`, and prior step outputs via `ctx["steps"]`.
