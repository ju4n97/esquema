# Request lifecycle

hclapi operates in two distinct phases: compile-time validation at boot, and fast sequential pipeline execution per request.

| Phase       | Trigger              | Actions                                                                                             | On failure                                              |
| :---------- | :------------------- | :-------------------------------------------------------------------------------------------------- | :------------------------------------------------------ |
| **Boot**    | `hclapi serve` boots | Discovers files, opens connection pools, precompiles Starlark scripts, and caches OpenAPI documents | Halts immediately with a clear terminal diagnostic      |
| **Request** | HTTP call arrives    | Enforces size limits, validates inputs, executes steps, and streams response                        | Returns an RFC 9457 error payload; server keeps running |

## Execution stages

1. **Telemetry & trace extraction**
   - Extracts incoming W3C `traceparent` headers.
   - Starts a root server span and mounts the panic recovery boundary.

2. **Payload boundary enforcement**
   - Reads request body via an `io.LimitReader` bounded by `server.max_body_size`.
   - Rejects oversized payloads with HTTP 413.

3. **Ingress validation & coercion**
   - Validates path, query, header, and body data against declared constraints.
   - Rejects violations with RFC 9457 HTTP 422 (or HTTP 400 for malformed JSON).
   - Coerces valid scalar parameters into native `int64`, `float64`, and `bool` types.

4. **Context initialization**
   - Builds the request-scoped `ctx` object with a frozen reference timestamp.

5. **Sequential step execution**
   - Runs declared steps (`sql`, `http`, `valkey`, `starlark`, `go`) one by one.
   - Emits individual OpenTelemetry child spans for each step and saves results into context.
