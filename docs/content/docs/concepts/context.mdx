# Execution context

Every request initializes an execution context container. It stores incoming request coordinates, frozen timestamps, and the outputs produced by executed pipeline steps.

```text
ctx
├── timestamp : int (Unix epoch seconds)
├── now       : string (RFC 3339 UTC timestamp)
└── request
    ├── method  : string ("GET", "POST", etc.)
    ├── path    : map[string]any (coerced int64, float64, bool, or string)
    ├── query   : map[string]any (coerced scalar or []any)
    ├── headers : map[string]string (lowercased header values)
    └── body    : map[string]any (parsed JSON body or raw text)

steps
└── <step_name>
    ├── rows          : list of map (all returned SQL rows)
    ├── row           : map or null (first SQL row)
    ├── rows_affected : int (number of rows returned, inserted, or updated)
    ├── status        : int (outbound HTTP status code)
    ├── body          : any (outbound HTTP response payload)
    ├── found         : bool (Valkey cache hit flag)
    ├── value         : any (Valkey cached payload or null)
    ├── success       : bool (Valkey write or delete flag)
    ├── stream        : iterator or reader (from streaming sql, valkey, or http steps)
    └── result        : any (value returned by Starlark or Go steps)
```

## Accessing data in HCL expressions

You can access context coordinates directly using standard dot syntax in step attributes:

```hcl
sql "update_user" {
  connection = "main"
  query      = "UPDATE users SET email = @email WHERE id = @id"
  args = {
    id    = ctx.request.path.id
    email = ctx.request.body.email
  }
}
```

Headers are normalized to lowercase per RFC 9110 (`ctx.request.headers.x-api-key`).

## Accessing data in Starlark

In Starlark scripts, `ctx` is passed as a standard dictionary to your `execute(ctx)` function:

```python
def execute(ctx):
    user_id = ctx["request"]["path"]["id"]
    body = ctx["request"]["body"]
    user_row = ctx["steps"]["find_user"]["row"]

    return {
        "user_id": user_id,
        "email": body.get("email", "").strip().lower(),
        "role": user_row.get("role", "member"),
        "processed_at": ctx["now"],
    }
```

## Accessing data in native Go steps

In Go callbacks, extract parameters safely using `req.Args`:

```go
func handleStep(ctx context.Context, in *hclapi.StepInput) (any, error) {
    userID := in.Args.GetOr("id", int64(0))
    email, ok := in.Args.Get[string]("email")
    rawRequest := in.Request // Raw standard *http.Request

    return map[string]any{"id": userID, "email": email}, nil
}
```

## Streaming context outputs (`steps.<name>.stream`)

When steps operate in streaming mode, they publish an iterator or reader under `steps.<name>.stream`:

- **`sql "fetch" { stream = true ... }`**: Publishes a `manifest.RecordSeq` (`iter.Seq2[any, error]`) that streams rows on-demand.
- **`valkey "sub" { op = "subscribe" channel = ... }`**: Publishes a live `manifest.RecordSeq` stream of pub/sub messages.
- **`http "proxy" { stream = true ... }`**: Publishes the live upstream socket as an `io.ReadCloser`.

Pipe these streams directly into a terminal `stream` step without buffering:

```hcl
stream "sse" {
  source = steps.sub.stream
  event  = "update"
}
```
